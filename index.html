Summary

Status: draft, 2026-11-10. Not built.

The notes at the end map each part of this summary to the requirements it meets, group by group. Every group of requirements has a note.

Summary · 01

The proposal

MetaLeX wants to run its Cybercorps contracts privately, with an independent operator who can recover every issuer's records. MetaLeX's own plan does this with one shared private chain on ZKsync Prividium. This proposal does it differently, with the same contracts and no changes to them.1

Each issuer gets its own EVM state. Three operators run it together: MetaLeX, an independent recovery operator, and the issuer. This group is the issuer's watcher party. Once a day, the watcher party posts a fingerprint of the state, its root, to a contract on Ethereum. Any two of the three operators can sign a root, so no single operator can stop an issuer or change its records alone.2

Operator keys run the system, but they hold no corporate authority. Corporate authority stays in the contracts, and no operator key can sign for a user.3

Money does not live in the private state. It stays on Ethereum in armada-nitro, Armada's payment system: shielded notes, and payment channels funded from notes. A buyer pays by a signed armada-nitro payment in its own channel. The private state sees that payment only as a balance, and every payee is paid out in armada-nitro.4

Summary · 02

What MetaLeX and its users get

  • Privacy between issuers. Each issuer's records are in a separate state. No issuer can read another issuer's data through any interface. A holder sees only its own records. MetaLeX and the recovery operator see everything, as MetaLeX's plan accepts.5
  • Recovery without MetaLeX. The recovery operator and the issuer hold the full state, and either can continue with the other. No promotion step and no MetaLeX signature is needed.6
  • Verified self-help for holders. Each holder can recover its own records and check them cryptographically against the roots on Ethereum, with no operator involved. It needs only its own stored records and the public blob data.7
  • Safe money. No operator can take a user's funds. A user can always exit a channel on Ethereum with its latest signed state.4
  • Wrapped scrip on Ethereum. A holder can lock scrip in the issuer state and receive the same amount of wrapped scrip on Ethereum, as notes. MetaLeX's bridge accounting holds unchanged, and every lock, mint and return is a signed record.89
  • The issuer's own records. The issuer is one of the operators. So it holds its full state and history, and it can export them without anyone's permission.10
  • Departure. An issuer can leave for a new set of operators. Its holders prove their records to the new operators.11
  • Any interface. MetaLeX's web app needs no new transport. Any other interface gets the same standard endpoint, with the same scope and checks.12
Summary · 03

How it differs from Prividium

Prividium proves every batch with a zkEVM on GPU hardware. This proposal does not need one for a reasonable level of safety. It relies on three things instead:

  • every root is a signed commitment that the operators cannot deny;
  • each holder checks its own records against every root;
  • a published conservation proof shows that no wrapped scrip exists without locked scrip behind it. Anyone can check it.

So a dishonest majority of operators could sign a wrong root, and Ethereum would accept it. But every holder would detect the change, and the signed root is evidence against those operators. Prividium's zkEVM would reject such a root. A zkEVM can be added later if MetaLeX wants that protection.13

Prividium keeps transaction data and state off chain, in the operators' databases. So a Prividium holder needs an operator to read or prove its records. In this proposal, a holder does not.14

Summary · 04

What it costs

On the same basis as MetaLeX's own cost tables, this design costs about $4,400 per month. That includes $1,449 that the issuers pay for their own watcher members. Prividium's three scenarios cost $4,600, $7,700 and $11,300 per month. The cost comparison gives every line.

Summary · 05

What MetaLeX must trust

  • The operators, for correct records. A wrong record is detectable and provable, but Ethereum does not block it.
  • The sequencer, to accept writes. A refused write has no remedy on Ethereum. The user's evidence goes to MetaLeX.
  • A watchtower, to protect an offline user's channel. The MetaLeX hub runs one for website users.15
Summary · 06

What MetaLeX must decide

  1. Which companies share one issuer state.
  2. Whether to accept the requirements: the 65 from MetaLeX's plan, and the 46 from this design.16

Document 02

Requirements of the system

Status: draft for review, 2026-11-11.

The system must keep 65 requirements from MetaLeX's plan (I-1 to I-65) and 46 from Armada's design (R-1 to R-46). MetaLeX accepts both lists as the requirements of the system, and an objection names the ID it concerns. Each group below has one sentence. Open a group to see its requirements. Section numbers refer to System design.

Requirements · 01

1. From MetaLeX's plan (I-1 to I-65)

Armada read MetaLeX's plan once and took out every statement of something the system must keep. Each requirement below quotes the sentence in the plan that states it. A script checked that each quotation appears word for word in the plan. One reading can miss a requirement, so a second, independent reading is the check for that.

Each requirement also says how this design holds it. 44 hold by design: a mechanism in the design makes them true. 20 hold once built: they need ordinary engineering, the same work that MetaLeX's own design needs. One holds in part, and its explanation says which part is still open.

Protocol and portability

The unchanged Cybercorps contracts run in an embedded EVM with a pinned release, and each issuer state has its own chain ID.

I-1 to I-9 (9 requirements)

I-1. The system keeps one EVM-native Cybercorps protocol on public and private chains, with no note-based or UTXO redesign.

How the design holds it (by design): The contracts run unchanged in the nimbus EVM (§3). Value stays in armada-nitro, so no note model touches Cybercorps state (§9).

MetaLeX's plan, Summary: "a note-based redesign is excluded"

I-2. The design preserves CyberCorp authority, LET legal-owner and custody distinctions, agreement identities, escrow obligations, scrip accounting and recertification rules.

How the design holds it (by design): The contracts and their bytecode run unchanged (§3).

MetaLeX's plan, §1, "One EVM protocol architecture is a fixed requirement": "Preserve CyberCorp authority, LET legal-owner/custody distinctions, agreement identities, escrow obligations, scrip accounting and recertification rules."

I-3. Every chain runs the same contract release, the same storage meanings and the same business transitions.

How the design holds it (by design): Every watcher member runs one pinned nimbus EVM commit and hardfork (§3).

MetaLeX's plan, §1, Table 02: "Same supported contract release, storage meanings and business transitions"

I-4. A signature is bound to its own domain, so no historical signature is a portable authorization.

How the design holds it (by design): Each issuer state has its own chainid, so a signature for one issuer state is not valid in another (§3).

MetaLeX's plan, §1, Table 02: "historical signatures are not portable authorizations"

I-5. Contract rights never depend on a Prividium login.

How the design holds it (by design): The contracts take no login as input (§8.1).

MetaLeX's plan, §1, Table 02: "Contract rights do not depend on a Prividium login"

I-6. An unknown capability refuses the operation it would otherwise grant.

How the design holds it (once built): Runtime manifest in the harness and the deploy module.

MetaLeX's plan, §1, "Source capability and deployed capability remain separate": "Unknown capabilities refuse the relevant operation."

I-7. The system deploys the full corporate graph, and it stores code hashes, ABI and storage-layout digests together.

How the design holds it (once built): Deploy module for the full graph. Each code hash is in the state root, so holders check it (§8.2).

MetaLeX's plan, §2, "Deploy the complete corporate graph": "Store compiler settings, link addresses, initialization transactions, ABI and storage-layout digests with the code hashes."

I-8. The pilot creates fresh companies only, and it migrates no existing company or legacy flow.

How the design holds it (by design): The deployment creates fresh companies only. It migrates no existing company.

MetaLeX's plan, §1, "Source capability and deployed capability remain separate": "it does not migrate existing companies or silently upgrade legacy/v4 flows"

I-9. Upgrade methods allow no arbitrary issuer recovery code, and factory reference implementations constrain them.

How the design holds it (by design): Enforced by the unchanged factory and beacon contracts.

MetaLeX's plan, §2, Table 04: "Existing upgrade methods do not allow arbitrary issuer recovery code."

Authority

Operator keys and data keys hold no corporate authority, and the recovery operator cannot create balances or sign for a user.

I-10 to I-13 (4 requirements)

I-10. An access administrator is not corporate authority.

How the design holds it (by design): Corporate authority stays in the contracts. The read scope uses that authority and holds none (§8.4).

MetaLeX's plan, §2, Table 04: "do not interpret an access administrator as corporate authority"

I-11. The system enumerates every privileged account and maps every bridge key to an actor.

How the design holds it (once built): Key inventory: party keys and bridge keys (§4.1).

MetaLeX's plan, §4, Table 07: "Every release/upgrade/pause key mapped to an actor"

I-12. The recovery operator cannot invent balances, sign as users or choose beneficiaries.

How the design holds it (in part): The recovery operator alone cannot sign a root: the party key needs a two-thirds majority of shares (§4.1). With one other watcher member it can sign a root that misaccounts. That root binds them, holders detect it, and the conservation proof catches supply that is not backed (§11). Watcher members hold no user keys.

MetaLeX's plan, §4, Table 07: "No power to invent balances, sign as users or choose beneficiaries"

I-13. A data key never authorizes a transaction, a registry signature or a bridge release.

How the design holds it (by design): No data keys exist: blob data is blinded, not encrypted (§7).

MetaLeX's plan, §3, "Specify the bundle before building its exporter": "Data keys never authorize transactions, registry signatures or bridge releases."

LET and scrip

Scrip is locked, not burned, when it leaves the issuer state, and LET custody and legal ownership stay as the contracts define them.

I-14 to I-23 (10 requirements)

I-14. Custody and legal ownership stay distinct, so a custody transfer alone changes no legal owner.

How the design holds it (by design): The Cybercorps contracts already enforce this rule, and they run unchanged.

MetaLeX's plan, §5, Table 10: "custody transfer alone changes no legal owner"

I-15. Scripification acts for the actual caller, so a relay cannot act on behalf of a holder.

How the design holds it (by design): The Cybercorps contracts already enforce this rule, and they run unchanged.

MetaLeX's plan, §2, "Why the first bridge locks canonical scrip": "A relay contract cannot simply call on behalf of a holder: its own address becomes the caller."

I-16. A void, frozen or reserved LET refuses every prohibited operation, and a restore keeps the endorsement floor.

How the design holds it (by design): The Cybercorps contracts already enforce this rule, and they run unchanged.

MetaLeX's plan, §5, Table 10: "All prohibited operations refuse; endorsement floor preserved."

I-17. Only the IssuanceManager mints or burns canonical scrip, and the ordinary bridge cannot mint or burn it.

How the design holds it (by design): The party custodian mints only the issuer's wrapper, never canonical scrip (§10).

MetaLeX's plan, §5, Table 10: "Ordinary bridge cannot mint/burn"

I-18. The scrip ratio cannot change while canonical supply is nonzero, so the bridge locks scrip instead.

How the design holds it (by design): Contract rule. The bridge locks, as mlx §2 specifies (§10).

MetaLeX's plan, §2, "Why the first bridge locks canonical scrip": "the scrip ratio cannot change while canonical totalSupply() is nonzero"

I-19. No force action destroys or moves locked collateral while wrapped scrip remains outstanding.

How the design holds it (by design): Entry guard on the lock: force features off, no restriction hooks, pinned implementation (§5.4). A hook added later that blocks an unlock is a signed misaccounting (§5.4, §11). Beacon upgrades with outstanding wrapped-scrip notes belong to mlx's powers review.

MetaLeX's plan, §2, "Why the first bridge locks canonical scrip": "they must not destroy or move collateral while public wrappers remain outstanding"

I-20. A private holder limit does not constrain wrapped scrip, and wrapped scrip states its own transfer policy.

How the design holds it (by design): The wrapper is a plain ERC20 held as notes. Unshielded, it moves as a plain ERC20, and no private holder limit applies to it (§10).

MetaLeX's plan, §2, "Why the first bridge locks canonical scrip": "Define freeze handling and the wrapper's public transfer policy explicitly."

I-21. Bridge return and recertification stay distinct, so a public purchaser does not inherit recertification eligibility.

How the design holds it (by design): The Cybercorps contracts already enforce this rule, and they run unchanged.

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "A public purchaser does not automatically inherit immediate recertification eligibility."

I-22. The system preserves the raw pool state, keeps attribution within the aggregate, and never lets an ERC20 transfer move attribution.

How the design holds it (by design): The Cybercorps contracts already enforce this rule, and they run unchanged.

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "ERC20 transfers do not transfer LET attribution."

I-23. The system does not assert exact equality between token supply and underlying units under floor rounding.

How the design holds it (by design): The design keeps this accounting rule from MetaLeX's plan unchanged.

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "do not assert exact equality between all token supply and underlying units"

Bridge accounting

Locked scrip equals the supply of scrip tokens outside the issuer state plus pending locks and returns, and the conservation proof shows this at each root.

I-24 to I-27 (4 requirements)

I-24. Canonical scrip supply equals the balances outside the bridge escrow plus the escrow balance, and the escrow balance equals locked backing plus surplus.

How the design holds it (once built): The watcher party keeps MetaLeX's accounting over locks, wrapped-scrip supply and returns (§10).

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "Enforce S = F + B = F + K + X and B = K + X."

I-25. At every reconciled checkpoint, locked backing equals wrapped-scrip supply plus locks awaiting a mint plus returns awaiting release.

How the design holds it (by design): The conservation proof shows it at every hard-final root (§11).

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "K = public wrapper supply Q + outbound locks awaiting mint O + public burns awaiting release R"

I-26. An unsolicited donation to the escrow raises only its balance and surplus, never wrapped-scrip mint authority or bridge liabilities.

How the design holds it (once built): The watcher party keeps MetaLeX's accounting over locks, wrapped-scrip supply and returns (§10).

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "An unsolicited donation increases B and X, never wrapper mint authority or bridge liabilities."

I-27. The system keeps explicit liabilities, and it never infers issuance from an escrow balance.

How the design holds it (once built): The watcher party keeps MetaLeX's accounting over locks, wrapped-scrip supply and returns (§10).

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "Maintain liabilities rather than inferring issuance from an escrow balance."

Bridge messages

Each lock and return record binds every message field, waits for finality, and has exactly one disposition.

I-28 to I-33 (6 requirements)

I-28. Each BridgeMessageV1 binds protocol, asset, chains, gateways, epochs, direction, nonce, parties, amount and source event.

How the design holds it (once built): Each lock and return record binds issuer, epoch, direction, asset, holder, note key, amount, nonce and source event (§5.4).

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "Each proposed BridgeMessageV1 binds protocol/version"

I-29. A wrong field, proof or finality check makes the message refuse without changing any balance.

How the design holds it (once built): The party custodian refuses a mint or return whose record does not match a lock or a wrapped-scrip payment (§5.4, §10).

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "refuses without balance change"

I-30. The system consumes each message once, and gives it exactly one release or recovery disposition.

How the design holds it (by design): Each lock is wrapped once, and each return is unlocked once (§5.4).

MetaLeX's plan, §5, Table 10: "Exactly one valid release or defined recovery disposition; no double refund."

I-31. An expiry never leaves a burned token with neither a release nor a refund.

How the design holds it (once built): Every return is unlocked by the watcher party (§5.4).

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "Expiry cannot leave a burned public token with neither release nor authenticated refund."

I-32. The system waits for source finality, so a reorg leaves no unbacked supply.

How the design holds it (by design): The party custodian mints only for locks in hard-final batches, and the RootChain accepts one successor per root (§5.1, §5.4, §6.1). No L1 check enforces the first rule; the signed mint record binds the watcher party (§11).

MetaLeX's plan, §5, Table 10: "Waits for finality; authenticated completion/refund; no unbacked supply."

I-33. Each message status is an independent fact, not one combined checkmark.

How the design holds it (by design): mlx's six statuses map onto the scrip lock's states, with message-proven replaced by the watcher party's signed record (§5.4).

MetaLeX's plan, §2, "Execute and reconcile the full round trip": "these are independent facts, not one green checkmark"

Privacy and access

Each issuer's records are in a separate state, and every read is scoped by the contracts' own authority.

I-34. LETs and their corporate, agreement and payment state stay private, while public scrip exposes addresses, amounts and timing.

How the design holds it (by design): One state per issuer; blob data is blinded (§3, §7).

MetaLeX's plan, Summary: "Keep LETs and their supporting corporate, agreement and payment state private"

I-35. MetaLeX and the recovery operator are the only accepted plaintext audiences.

How the design holds it (by design): The watcher members hold plaintext: MetaLeX core, the recovery operator and the issuer (§4). MetaLeX is a plaintext audience through the MetaLeX hub (R-36). Holds if the watcher members are bound to their principals.

MetaLeX's plan, §1, "Orientation": "The design accepts MetaLeX and that operator as plaintext audiences."

I-36. No interface lets one issuer's data leak into a cross-issuer read.

How the design holds it (by design): One state per issuer: no other issuer's data exists in it (§3).

MetaLeX's plan, §5, Table 10: "No unauthorized fields or rows returned."

I-37. A holder sees less data than an issuer officer sees.

How the design holds it (by design): The party RPC scopes every read by the contracts' own authority, so a holder sees less than an issuer officer (§8.4).

MetaLeX's plan, §4, "Isolate issuers without changing the EVM state model": "Holder access is narrower than issuer-officer access"

I-38. Access to one agreement does not reveal another issuer's agreement, even by a changed ID.

How the design holds it (by design): Per-issuer registries plus the read scope (§3, §8.4).

MetaLeX's plan, §4, "Adapt actual application transports and call paths": "access to one agreement must not reveal another issuer's agreement by changing its ID"

I-39. The system controls nested call paths, because top-level selector allowlists alone are not sufficient.

How the design holds it (by design): Call-trace inspector on every frame before sequencing (§8.5).

MetaLeX's plan, §4, "Isolate issuers without changing the EVM state model": "top-level selector allowlists alone are insufficient"

I-40. No shared client cache holds a user credential, and the system fails closed on an authentication failure.

How the design holds it (once built): MetaLeX app transport changes and the party RPC's request signatures (mlx A1, §8.1, §8.5).

MetaLeX's plan, §4, "Adapt actual application transports and call paths": "fail closed on private-chain authentication failure"

I-41. The system promises protected record access, not zero observable information.

How the design holds it (by design): Stated scope. Blob data reveals change counts, timing, and that the same position changed again (§7).

MetaLeX's plan, §4, "Isolate issuers without changing the EVM state model": "promise protected record access rather than zero observable information"

Recovery

A root is final only after t watcher members store its batch, and any t watcher members continue with no promotion step.

I-42 to I-51 (10 requirements)

I-42. The system never rolls back past a public bridge obligation and calls the result current.

How the design holds it (by design): Only hard-final batches affect anything outside the issuer state, and hard-final roots cannot be replaced (§5.1).

MetaLeX's plan, §3, "P2 recovery is operational; P3 adds enforceable departure": "never roll back past a public bridge obligation and call the result current"

I-43. The system loses no finalized obligation.

How the design holds it (by design): A root is hard-final only with the party signature. A watcher member signs only after it stores the batch, so t watcher members hold every hard-final batch (§4.2, §6.1). Holders also keep their own records (§8.1).

MetaLeX's plan, §3, "P2 recovery is operational; P3 adds enforceable departure": "no loss of finalized obligations"

I-44. If data or authority is missing, the recovery drill fails.

How the design holds it (once built): The watcher members run recovery drills. A drill fails when data or authority is missing.

MetaLeX's plan, §3, "P2 recovery is operational; P3 adds enforceable departure": "If data or authority is missing, the drill fails."

I-45. Two operators cannot continue conflicting operation, because DNS failover alone is not sufficient.

How the design holds it (by design): One successor per root on L1, and two successors of one root are slashable (§4.4, §6.1).

MetaLeX's plan, §3, "P2 recovery is operational; P3 adds enforceable departure": "DNS failover is insufficient."

I-46. Promotion needs no MetaLeX signature and no discretionary vendor permission.

How the design holds it (by design): No promotion step. Any t watcher members continue, and no signing set needs MetaLeX's share (§4.1, §6.2).

MetaLeX's plan, §3, "P2 recovery is operational; P3 adds enforceable departure": "If promotion requires an unavailable MetaLeX signature or discretionary vendor permission, independent recovery has failed."

I-47. An immutable recovery copy survives a mistake that was replicated into the live database.

How the design holds it (by design): Blob data on L1 cannot be changed, and every watcher member archives it (§7). Each wallet also keeps its latest proof of each record.

The issuer stops

Fewer than t watcher members are live

MetaLeX on Armada: system design

Status: draft for review, 2026-11-09. Not built.

MetaLeX's Cybercorps contracts run unchanged, but not on one shared chain. Each issuer gets its own EVM state, the issuer state. A small group of operators, the issuer's watcher party, runs that state. The group has three watcher members: MetaLeX, an independent recovery operator, and the issuer.

Once a day, the watcher party posts a fingerprint of the state, its root, to an Ethereum contract: the issuer's RootChain. Each holder keeps proofs of its own records against those roots. So a holder can show what it owns, even if every operator fails.

Money does not live in the issuer state. It stays in armada-nitro, Armada's payment system on Ethereum. There, value is either a shielded note in the Armada pool, or a balance in a payment channel that a note funds. A buyer's USDC stays in the buyer's own channel until the deal settles. Scrip that leaves the issuer state becomes notes of an issuer-specific token, the issuer's wrapper.

The design has no zkEVM and no GPU prover. It does not need one for a reasonable level of safety (§11). It relies on three other things instead:

  • signed commitments that the operators cannot deny;
  • proofs that each holder checks itself;
  • a conservation proof that anyone can check.

Short citations such as cc or mlx refer to the sources at the end. Requirements lists the requirements that this document holds. Terms follow Glossary.

System design · 01

1. Requirements

  1. Run the unchanged Cybercorps contracts.
  2. Keep each issuer's records readable only by MetaLeX, the recovery operator and the issuer.
  3. Let a holder prove its own MetaLeX assets against L1, and help itself if the issuer, MetaLeX and the recovery operator all fail.
  4. Keep all value in armada-nitro: shielded notes and channels.
  5. Let scrip leave the issuer state as armada-nitro notes, with MetaLeX's accounting.
  6. Define every component as a typed state machine with guarded transitions. No fallback paths.
  7. Let no party other than an asset holder start an action against that holder's assets.
System design · 02

2. Architecture

The parts of the system are on Ethereum L1, in each watcher party, or with MetaLeX.

On Ethereum L1

  • Issuer RootChain: An L1 contract, one per issuer. It stores the hard-final roots of the issuer state, one successor per root, each accepted on the party signature (§6).
  • Daily aggregator: An L1 contract. Once per day it records one Merkle root over every party's signed root, and the hashes of the blobs that carry their data (§6.2).
  • IssuerEpochRegistry: An L1 contract that records each departure: the old RootChain's final root and the successor's identity (§5.5).
  • Issuer wrapper: An ERC20 on L1, one per issuer, whose only minter is the party custodian. It is held as notes in the Armada pool (§10).
  • Wrapper factory: The L1 factory that deploys each issuer's wrapper. A hub names it in its asset list (§10).

Run by each watcher party

  • Issuer state: One EVM state per issuer: its Cybercorps companies, its channel-balance contract and its payout records (§3).
  • Watcher party: An entity: the threshold signer that runs one issuer state and anchors it to L1. Through its custodian it is also an armada-nitro participant and the minter of the issuer's wrapper (§4).
  • Party custodian: The watcher party's HubCustodian, a smart wallet. It signs the watcher party's channel states and wrapped-scrip mints with the FROST party key (§4.1).
  • Party RPC: The watcher party's own private RPC, in MetaLeX's sense. The only interface to the issuer state (§8.1).
  • Channel-balance contract: A system contract in the issuer state with an ERC20 interface. Each balance is USDC that a holder committed to the watcher party in armada-nitro and has not yet withdrawn (§9.2).
  • Party bond: One armada-nitro channel per watcher party (§4.4).

Run by MetaLeX, or by anyone

  • MetaLeX hub: An armada-nitro hub, and an entity distinct from MetaLeX, the company. As MetaLeX core it is a watcher member of every party. MetaLeX is a plaintext audience through it. It routes payments, runs watchtowers for website users, and supplies user IDs to each issuer state (§8.1, §9).
  • Verifier tool: A tool that reads a root and the issuer wrapper's supply from L1, and checks the conservation proof against them (§11).

4. Watcher parties

A watcher party is a bonded group of operators, in the sense of Armada's glossary (t2). In this design, each watcher party serves one issuer. It runs the issuer's state and anchors it to Ethereum. It is also an armada-nitro participant: it holds channels, receives payments and pays withdrawals.

4.1 Composition

Each issuer has one watcher party, and MetaLeX's whole platform is the set of these parties. A watcher party has three watcher members: MetaLeX core, the recovery operator and the issuer (n = 3). MetaLeX core is the MetaLeX hub in its role as a watcher member of every party. It sequences by default, and MetaLeX is a plaintext audience through it.

Keys. Each party has one FROST threshold key, the party key. Its threshold t is a two-thirds majority of n, a parameter of the deployment. With n = 3, t = 2. So any two watcher members can sign, and no signing set needs MetaLeX's share.

Custodian. On L1, the party acts through its party custodian: a HubCustodian under the party key (nitro src/HubCustodian.sol). It is a smart wallet: the party's EIP-1271 identity in its channels, and the only minter of the issuer's wrapper. It signs every channel state with the FROST party key. A FROST signing round among the watcher members takes one network round trip, far less than Ethereum's 12-second block time.

Liveness. The system's liveness never depends on the MetaLeX hub: any t watcher members continue the RootChain and the pay-outs without it. With n = 3 and MetaLeX core down, an issuer's RootChain advances only while that issuer's watcher member is up.

4.2 Duties

  1. Sequence and execute the issuer state. MetaLeX core does this by default.
  2. Sign hard-final roots with the party key (§6). A watcher member contributes its signature share only after it stores the batch durably, so at least t watcher members hold every hard-final batch.
  3. Publish each batch's blinded tree data in blobs (§7).
  4. Keep the channel balances: apply each co-signed state from Nitro p2p in its next batch. Pay each withdrawal through armada-nitro once its batch is hard final (§9.2). Mint and burn the issuer's wrapper (§10).
  5. Publish a conservation proof for each hard-final root (§11).
  6. Run the party RPC, which serves each holder its records, salts and proofs (§8.1).

4.3 Storage

Each watcher member stores the full state and history itself: every block, receipt, log, salt and position salt. L1 does not rebuild a watcher member's state, because the blobs are blinded. A party continues as long as t of its watcher members hold the state.

4.4 Bond

Each party bonds through one armada-nitro channel. Its participants are the party custodian and a slashing arbiter. The arbiter is an EIP-1271 participant that signs only a state with a valid fault proof. So no one can slash the bond without such a proof. The watcher members fund the bond, and how they share a slash is their own agreement.

System design · 06

6. RootChain rules

6.1 Root acceptance

The RootChain accepts a root, directly or by inclusion proof from the daily aggregator (§6.2), only if all of these hold:

  1. One successor. prevRoot equals the last hard-final root, and height is the last height plus one.
  2. Party signature. The party key signed (prevRoot, newRoot, height, batchCommitment, eventsRoot, chainConfigHash, blobRefs).
  3. Blob binding. blobRefs lists the versioned hashes of the blobs that carry this party's data, with its offset and length in each. Every hash is one that the aggregator recorded as published, or one in the root's own blob transaction.

The RootChain only stores roots. It checks no validity proof (§11) and acts on no message.

6.2 Daily aggregation

By default, MetaLeX core publishes all parties' roots of the day in one run:

  1. Blobs, packed by size. The blob data of every party with changes is concatenated and split into blobs. One blob transaction holds up to Ethereum's per-transaction blob limit; a day that needs more uses more blob transactions.
  2. One aggregation call. The first blob transaction calls the aggregator. It records the versioned hashes of the day's blobs and one Merkle root over the day's signed party roots.
  3. Lazy RootChain reads. A RootChain reads its root from the aggregator by inclusion proof only when an L1 action needs it, for example a departure. Holders check the inclusion proof off chain (§8.2).

Each party still signs only its own root and its own blob references. A party with no changes is absent from the day's tree, and posts nothing. Any t watcher members of a party may submit their root directly to their RootChain, in their own blob transaction, by the same rules. That is the same transition, not a second path.

System design · 07

7. Blob data: blinded, not encrypted

Each root publishes, in blobs, the blinded position and blinded leaf of every slot whose value changed since the previous root. A slot that changed several times since the previous root appears once, with its final value. Interior nodes are not published: anyone with the archived leaves rebuilds the tree.

Holders who want durable records use Armada's mobile app, which contains the website and a watcher for the holder's own records. Browser storage holds the same data, but it is more easily deleted.

System design · 08

8. Holders

8.1 The party RPC

Each watcher party runs its own RPC, in MetaLeX's sense of the word: the private, authenticated endpoint that mlx puts in front of the chain ("Private RPC/policy enforcement", Table 02). It is the only interface to the issuer state. Any watcher member may run an endpoint of it. MetaLeX core runs one by default.

For each hard-final batch that changes a holder's records, the party RPC gives the holder: - each changed value, its new salt and its position salt; - the logs that touch the holder's records; - a proof of each record against the new root.

A holder subscribes for these, or fetches them. Every item verifies against a root on L1.

Authentication. The issuer state gets user IDs from the MetaLeX hub. A user signs each request to the party RPC with its wallet key, through MetaLeX's existing wallet login (mlx §4: the Privy-aware wallet abstraction). The party RPC checks the signature against the ID in the issuer state, and scopes the request by the contracts' authority for that address (§8.4). The hub is not in the request path, so a user reads its records while MetaLeX core is down. Authentication establishes identity only. Rights stay in the contracts.

8.2 Verification

  1. Read the root from the RootChain through a light client: Armada's nimbus verified proxy.
  2. Check each record with the JMT verifier from lib/, compiled to WASM with the nimbus toolchain: the same Nim code that the harness runs.
  3. Check the code. The same root commits to each contract's code hash. The holder decodes slots with the storage layout that MetaLeX's deployment manifest pins for that code hash.
  4. Check completeness of its history: every change of value between consecutive roots must be explained by logs in eventsRoot.
  5. Check every new root. The verifier checks each of the holder's records against each new hard-final root. If a proof fails and the party RPC delivered no update, the verifier reads that root's blobs to find the change (§7). The mobile app does this itself. The website does it while it is open.

So a holder detects any change to its own records, even when the party RPC is silent. It can also prove what it held at any root.

8.3 Self-help

The issuer, MetaLeX and the recovery operator can all fail. A holder then uses only L1 and what it holds in browser storage or in the app (§7): - its values, salts and position salts from §8.1; - the archived blob data, from which it rebuilds the tree.

From these it computes a proof of each record against the last root. That proof shows what the holder owned. If the issuer departs to a successor, the holder proves its records to the successor's watcher party with the same proof, off L1 (§5.5).

8.4 Scope

A holder sees its own records under the contracts' own authority: its LETs, scrip, channel balance, endorsements, agreements and grants. It sees an asset's history only from the batch in which it first holds the asset. Earlier holders are other counterparties of the issuer, and no counterparty sees another counterparty's private data. Issuer officers see every counterparty's data. MetaLeX, through the MetaLeX hub, and the recovery operator see everything, as the named plaintext audiences.

8.5 Methods and writes

The party RPC serves MetaLeX's app with eth_sendRawTransaction, eth_getTransactionReceipt, eth_call and eth_getLogs, each scoped by the contracts' authority (§8.4, mlx §4, A1). It adds methods for records, salts, proofs and history subscription. It has no unscoped method.

Writes go to the sequencer. Before sequencing, the harness executes each transaction with an inspector that checks every CALL, DELEGATECALL and CREATE frame against the policy. A transaction with a denied frame is not included.

The sequencer can also refuse a write. A payer whose write is refused gets no asset and has no remedy on L1. Its signed request and the refusal are its evidence to MetaLeX.

8.6 The web app's endpoint and indexing

MetaLeX's web app needs no new transport. The work splits between the party RPC and the browser:

Watchtowers. ForceMove protects a channel only if someone answers a stale-state challenge within the challenge window. The MetaLeX hub runs a watchtower for website users by default. The recovery operator may also run one. The mobile app runs its own.

9.2 The watcher party as a Nitro participant

The Cybercorps contracts pull, hold and pay an ERC20 in the same EVM (cc src/storage/LexScrowStorage.sol:251, 308). The USDC itself stays in armada-nitro. So the issuer state gets a view of it: the channel-balance contract, a system contract with an ERC20 interface. Each deal names it as paymentToken. Its balances are not a second asset. Each one is USDC that a holder committed to the watcher party in armada-nitro and has not yet withdrawn.

Channels. Each holder that pays or is paid has a channel with the watcher party, funded through a hub (§9.3). The party custodian is the watcher party's participant in it.

Paying in. The buyer and the watcher party co-sign a state that moves the amount from the buyer's allocation to the watcher party's. This is an ordinary armada-nitro payment. So the buyer cannot spend the amount again: it is no longer the buyer's allocation, and only a later co-signed state can change that. No separate lock is needed.

Crediting. The watcher party receives the co-signed state over Nitro's p2p transport (adr ADR-0008) as soon as the buyer signs it. In its next batch, it applies the state, and the channel-balance contract credits the buyer. The batch records the state's hash, so every watcher member replays the batch to the same result. The watcher party reads L1 only for events on the adjudicator: deposits, challenges and conclusions.

Inside the issuer state. The Cybercorps contracts move balances like any ERC20. signDealAndPay pulls the buyer's balance into escrow, finalizeEscrow pays the issuer and MetaLeX, and refundVoidedDeal returns it to the buyer.

Withdrawal. A holder withdraws by calling withdraw on the channel-balance contract. That is the holder's own transaction, and its balance falls by the amount. Once the batch is hard final, the watcher party pays the amount to the holder through armada-nitro, exactly once for each withdrawal. With each payment, the issuer state records a payout record: the withdrawal, the channelId and the hash of the co-signed state that paid it. The holder exits its channel to a fresh shielded note when it chooses, and unshields that note itself if it wants. So the issuer's RootChain points to the note, through the root.

Supply. The sum of all balances, plus withdrawals not yet paid, equals what the watcher party received through applied states, less what it paid out. The watcher party holds that USDC as its own allocations in armada-nitro channels. Every credit, withdrawal and payment is a co-signed state or a transaction in a signed root, so each holder can prove its own part (§11).

A buyer's challenge. A buyer could force-close its channel with an earlier state, from before its payment. The watcher party, or a watchtower, answers the challenge with the later co-signed state. ForceMove's turn rule decides, and no root is read (§9.1).

9.3 Routed payments through the MetaLeX hub

Value moves between channels as one Nitro payment routed through the MetaLeX hub's channels. Nitro's guarantees and reclaim make the move atomic across the hops, and ForceMove accepts or rejects whole states (adr ADR-0021 D21.1). The hub routes the payment and advances no value. No hash lock is used, and no party has value in flight.

A user that does not want the MetaLeX hub uses an issuer's hub, or a channel with the watcher party directly.

9.4 A primary deal, step by step

  1. The issuer proposes. An issuer officer calls DealManager.proposeDeal(certPrinter, paymentToken, paymentAmount, …) (cc src/DealManager.sol:144), with the channel-balance contract as paymentToken. The issuer state creates the agreement and an Escrow (LexScrowStorage.sol:184): corpAssets holds the LET, and buyerAssets holds the payment.
  2. The buyer pays in. The buyer and the watcher party co-sign a state in the buyer's channel that moves the amount to the watcher party (§9.2). In its next batch, the watcher party credits the buyer's balance.
  3. The buyer signs and pays. signDealAndPay (DealManager.sol:231) pulls the buyer's balance into LexScrow with safeTransferFrom (LexScrowStorage.sol:251). The escrow becomes PAID.
  4. The deal finalizes. finalizeDeal (DealManager.sol:271) runs finalizeEscrow (LexScrowStorage.sol:308). It moves the balance to companyPayable(), the issuer, and the fee to getPlatformPayable(), MetaLeX. It delivers the LET to the buyer, and legal title moves to the buyer that the latest endorsement names.
  5. The batch is anchored. The watcher members store the batch and sign it with the party key. MetaLeX core publishes the root in the daily run (§6.2).
  6. The issuer is paid. The issuer withdraws its balance. Once that batch is hard final, the watcher party pays the issuer through armada-nitro, and the issuer state records the payout record. The issuer exits to a shielded note when it chooses. MetaLeX's fee leaves the same way.
  7. Void. refundVoidedDeal (DealManager.sol:310) returns the balance to the buyer. The buyer keeps it for another deal, or withdraws it.
System design · 10

10. Scrip as armada-nitro notes

Scrip leaves the issuer state the way USDC enters it, in the opposite direction. Outside the issuer state it is wrapped scrip, held as notes, and it trades like any armada-nitro asset.

Out. 1. The holder locks canonical scrip in the issuer state and names its note key. The scrip is locked, not burned, because its ratio cannot change while canonical supply is above zero. The entry guard applies (§5.4). 2. Once the lock's batch is hard-final, the party custodian mints the same amount of wrapped scrip. It shields it as a note to the named key. The Armada pool accepts it, because the pool shields any ERC20 that is not on its blocklist.

In. 1. The holder pays wrapped scrip back to the party custodian, which burns it. 2. The watcher party unlocks the scrip to the holder in the issuer state.

In channels. A hub lists the assets that its channels hold: "The set of tokens the hub has configured for this adjudicator's channels" (nitro src/ArmadaNitroAdjudicator.sol:44). The list screens out tokens whose balances change other than by transfer (p15 I1), and it is fixed at deployment to keep governance off the settlement path. The list may name factories (adr ADR-0021 D21.2). A hub names the wrapper factory, so its channels accept every issuer's wrapper. Every such token is a plain ERC20 whose only minter is its party custodian, so it passes I1. The wrapper factory must therefore exist before the adjudicator that names it is deployed.

Accounting. mlx's identities apply unchanged: locked scrip K equals wrapped-scrip supply Q plus locks awaiting mint O plus returns awaiting unlock R. The lock and return records carry BridgeMessageV1's bindings (§5.4).

Transfer policy. A wrapped-scrip note can be unshielded like any note. The wrapped scrip then moves as a plain ERC20, and no private holder limit applies to it. A holder that returns wrapped scrip to scrip does not inherit recertification eligibility.

System design · 11

11. Trust without the zkEVM

Scope. A zkEVM is not required for a reasonable level of safety, so it is out of scope. The RootChain therefore accepts each root on the party signature alone (§6.1).

Every signed act is a binding commitment. The watcher party signs the roots, the channel states and the wrapped-scrip mints. Each signature binds it to what it records. A root that pays the issuer y USDC also records the n shares that the buyer receives for it. The commitment stays binding even if the operators fail to account for it in a later root.

System design · 13

13. Hash function choice and cost

13.1 The hash is a deployment parameter

  • lib/ builds the state tree and the events tree over a hash parameter. The harness and the WASM holder verifier use the same code. lib/ is Armada's own Nim implementation of the JMT, so it takes the hash as a parameter.
  • The choice is fixed per deployment. The hash identities are part of chainConfigHash, so each accepted root states its hashes.
  • Changing the hash of a live RootChain means a new RootChain, through the departure of §5.5.
  • L1 verifies no tree proof. A departure imports off L1 (§5.5).

13.2 Measured cost

Measured on 2026-11-09:

  • L1 gas: a Foundry test of one binary Merkle inclusion proof per hash.
  • Browser time: Bun with hash-wasm and @noble/hashes.
  • Native time: the Rust sha2 and sha3 crates.

The harness is Nim, so its native hash times are not yet measured.

SHA-256 is 2.7 to 3.9 times faster off chain. Through WebCrypto, SHA-256 measured 0.375 ms per depth-32 proof, because each call is asynchronous, so the verifier uses the WASM implementation. L1 checks no tree proof, so Keccak-256's lower gas does not matter. SHA-256 is therefore the default. The blinding salts (§3) use the state-tree hash.

The EVM computes keccak for the KECCAK256 opcode and for every mapping slot key. That cost is the same for every tree hash.

MetaLeX private-chain plan: invariant review

The requirements in MetaLeX's private-chain plan do not contradict each other. Three points are open: the plan states the requirement but leaves the rule that meets it undecided. This page quotes each requirement, shows the state transition it governs, and names the decision MetaLeX must make.

Review of MetaLeX's plan · 01

Source and method

Source. MetaLeX Engineering, Build MetaLeX's private chain with recovery, standalone edition, "Evidence as of 08 November 2026". Citations below give the plan's section heading and table number. Every quotation is verbatim. Vendor quotations come from the linked ZKsync and L2BEAT pages, read 9 November 2026.

Method. Armada extracted 65 invariants from the plan and checked each pair against the plan's state machine. That state machine has three participants, not two: MetaLeX as primary operator, the independent recovery operator, and the settlement contract on Ethereum. A pair counts as a conflict only if no state of that machine satisfies both. No pair does.

Open point. A requirement is open when the plan states what must hold, but does not fix how. The rule, the role or the guard that makes it hold is missing. An open point is a decision, not a defect.

Invariant IDs. The IDs (I-n) come from Armada's extraction, and match Requirements. The plan does not number its invariants.

Review of MetaLeX's plan · 03

Open point 1: the rule that moves submission authority

The requirements

Table 27Scroll horizontally ↔
ID Requirement Plan text Location
I-45 Fencing "The selected settlement/operating mechanism must revoke or supersede the old sequencer/proposer/submission authority and demonstrate that two operators cannot continue conflicting operation." §3, "P2 recovery is operational; P3 adds enforceable departure"
I-45 Not by network failover "DNS failover is insufficient." Same section
I-46 Promotion without MetaLeX "If promotion requires an unavailable MetaLeX signature or discretionary vendor permission, independent recovery has failed." Same section
I-12 The recovery operator's powers "The recovery vault needs infrastructure authority, never user transaction keys." Same section

The state transition

The settlement contract on Ethereum holds the submission authority. It accepts a batch only from the holder of that role. Promotion is one L1 transaction that moves the role from MetaLeX to the recovery operator. After that transaction, the contract rejects MetaLeX's batches. So the move itself fences the old writer, and two writers cannot both settle.

"Role moved on L1" is one L1 transaction under a rule fixed in advance. I-45 and I-46 both hold if the rule that moves the role does not need MetaLeX's signature. For example:

  • the recovery operator holds a key that may move the role; or
  • the role moves to the recovery operator when no batch settles for a fixed time.

What the plan leaves open

The plan requires the result but does not name:

  • which L1 role holds submission authority on the selected stack;
  • who may move that role, and under which rule;
  • whether that rule is already available on the selected release, or needs a change.

The plan's P0 asks for "independent operating rights", which is where this decision belongs.

A separate point that is not a conflict

The plan also says: "With only MetaLeX and one recovery operator, requiring both also gives either party a liveness veto." This sentence is about the gate on data delivery: whether each batch waits for the recovery operator's acknowledgment before it settles. It is a stated trade-off between waiting and not waiting. It does not affect who may submit batches, so it does not interact with fencing.

Open point 2: the guard on entry to the bridge

The requirements

Table 28Scroll horizontally ↔
ID Requirement Plan text Location
I-2 Preserve the protocol semantics "Preserve CyberCorp authority, LET legal-owner/custody distinctions, agreement identities, escrow obligations, scrip accounting and recertification rules." §1, "One EVM protocol architecture is a fixed requirement"
I-19 No collateral movement while wrappers exist "Disable optional force-transfer/force-burn features for this candidate asset: they must not destroy or move collateral while public wrappers remain outstanding." §2, "Why the first bridge locks canonical scrip"
I-20 The wrapper has its own policy "A private holder limit or whitelist does not automatically constrain the public wrapper; whitelisting the bridge address alone merely sees one private holder." Same section
I-20 The policy must be explicit "Define freeze handling and the wrapper's public transfer policy explicitly." Same section
— Upgrades can change the guard "Beacon upgrade powers can change these assumptions later and belong in the powers review." Same section

The state transition

Force-transfer and force-burn are optional features. Whether an asset enables them is configuration, not protocol semantics, so disabling them does not touch I-2. I-19 is then a guard on the lock transition: canonical scrip may enter the bridge escrow only from an asset whose force features are off.

The guard holds when the asset's force features are off and the wrapper's transfer policy is defined. I-20 is not a constraint on the private asset. The wrapper is a separate token, and the plan requires its transfer policy to be defined on its own.

What the plan leaves open

The plan states the guard for one asset only: the P1 candidate, which uses "fresh, homogeneous, fully paid synthetic LETs and a 1:1 base-unit ratio". For production it does not say:

  • which instrument classes may enter the bridge;
  • where the guard is checked: in the bridge escrow, in the issuer's configuration, or in operations;
  • what happens to outstanding wrappers if a beacon upgrade later turns a force feature back on.

If an issuer needs force actions or holder restrictions to reach wrapped holders, that is new scope. The plan lists it in Table 08 as "Extended restriction/force-action synchronization", for separate approval.

Open point 3: the meaning of the login sentence

The requirements

Table 29Scroll horizontally ↔
ID Requirement Plan text Location
I-5 Rights do not depend on a login "Contract rights do not depend on a Prividium login" §1, Table 02, row "Privacy and data access", column "Portable protocol requirement"
— Private access enforcement "Private RPC/policy enforcement and scoped indexers on Prividium" §1, Table 02, same row, column "Chain-specific configuration or adapter"
I-10 Authority stays in the contracts "Keep corporate authority in BorgAuth, the company/managers and user signatures." §1, "Default to Core; buy Commander only for demonstrated operating value"
I-40 Fail closed "fail closed on private-chain authentication failure" §4, "Adapt actual application transports and call paths"

Two readings

Reading A: the contracts define rights without a login. No contract check takes the login as an input. The gateway is an adapter in front of the contracts. The plan's layout supports this reading: Table 02 puts the sentence in the column "Portable protocol requirement" and puts the gateway in the column "Chain-specific configuration or adapter". Under this reading, nothing more is needed.

Reading B: a holder can always use the rights that the contracts record. On the selected stack, every request passes the gateway:

"All interactions — from users, enterprise applications, block explorers, or bridge operations — must pass through this proxy."

— ZKsync Docs, Prividium™ Architecture

The gateway fails closed (I-40), and the operator can filter transactions that come from L1 (ZKsync Docs, Transaction filtering). L2BEAT records that ZK Stack users "can submit transactions to an L1 queue, but can't force them" (L2BEAT, ZKsync Era). So reading B needs a forced-inclusion path for writes, which the plan does not have.

What the plan leaves open

Which reading MetaLeX intends. Table 07 lists "censorship" among the operator powers for legal review, which fits reading A.
